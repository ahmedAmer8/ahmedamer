I wrote a careful latency analysis, then measured it and two conclusions flipped

Six prioritised recommendations, reconstructed from log timestamps. When the tracing arrived, one was inverted, one was overstated by 3x, and the largest problem in the system was not in the document at all.

The document

Before the tracing existed I wrote an analysis of where an agent turn’s time was going. It had six prioritised fixes, each with an estimated saving and a rationale. It was cited in planning. It was careful work.

It was reconstructed from timestamps in token logs, which bracket model calls and nothing else.

What measurement did to it

Two conclusions inverted, one was out by a factor of three, and the single largest problem in the system did not appear anywhere in it.

The inversion is the one I think about most. The document recommended disabling the model’s reasoning budget on the main call, reasoning that it was pure overhead on a conversational turn. The spans showed that a greeting spends about 120 reasoning tokens, while a complex multi-item order spends 627.

So the saving is smallest exactly where disabling it would be safe — on a greeting — and largest exactly where the reasoning is doing the work that keeps an order correct. That recommendation is now marked not done, deliberately, which is a stronger statement than not done.

The thing the technique could not see

Reconstructing from token logs means your measurement surface is exactly the set of things that write token logs. Model calls do. Prompt construction does not.

So prompt construction had an implied cost of zero in every estimate in the document. It was, in fact, 19,369 database queries and about a third of all turn time.

Any measurement reconstructed from a proxy can only see what the proxy emits. Everything silent is scored zero, and the silent things are exactly the ones nobody has thought about yet.

Keeping the wrong document

The instinct after this was to rewrite the analysis so it said the right things. I did not, and I think that was the better call.

It now opens with a block stating plainly that its estimates predate the instrumentation and should not be trusted over the spans, followed by a table of which of its own recommendations measurement inverted. Anyone who read it before can see what changed and why. Anyone reading it now gets the correction before the content.

A silently corrected document teaches nobody anything, including its author. It also quietly destroys the record of how the estimate went wrong, which is the part worth keeping — the failure mode was not carelessness, it was a measurement surface that could not see past its own instrument.

Reporting what did not move

One more habit came out of this. The same analysis measured a change we had expected to help — reusing a single HTTPS connection for outbound sends — and found no effect at all. 580 ms before, 609 ms after, both inside the band of ordinary daily variation.

That null result is in the write-up, in the same table as the wins. It costs nothing to include and it is the main reason I believe the other numbers: a report that only contains improvements is a report that has been filtered, and you cannot tell by how much.

The principle

An estimate reconstructed from adjacent data is a hypothesis. Label it as one, and keep it visible after the measurement so the correction is legible.
