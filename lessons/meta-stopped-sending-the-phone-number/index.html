Meta stopped sending the phone number, and we dropped the message silently

WhatsApp began rolling out usernames. Senders who adopted one arrived with no phone number in the payload, our ingest discarded them with a bare continue, and nobody found out from an alert.

The investigation

observation — A customer said they had messaged and got nothing back.

A customer said they had messaged and got nothing back.

A single report. Nothing in the error rate, nothing in the dead-letter queues, nothing in the dashboards. From the inside the system looked entirely healthy — because from the system’s point of view, that message had never arrived.

assumption — We assumed it was a Meta-side delivery problem, and stopped looking.

Our own runbook for a silent WhatsApp number said: count the inbound messages we have ever seen for this tenant; if the count is unchanged, Meta is not calling us, and it is a platform-side configuration issue. That step is correct for every cause we had seen before. It reaches exactly the wrong conclusion here, because Meta was calling us. We were the ones throwing the message away.

dead end — Looking for an identifier-to-phone lookup.

Looking for an identifier-to-phone lookup.

The natural fix is to resolve the new identifier back to a phone number and carry on as before. There is no such API. We probed the endpoints directly rather than trusting documentation, and confirmed it: the phone number is available only if the customer has interacted recently or is already in the business’s contact store, and the identifier is scoped per business — the same person has a different one at each brand. Cross-tenant matching on it is impossible by design.

fix — Treat the identifier as a first-class address, and ask for the number when it matters.

Treat the identifier as a first-class address, and ask for the number when it matters.

Outbound sends now route by identifier shape. Customer identity is keyed on the pair of tenant and identifier, never the identifier alone — a global unique constraint would have been silently wrong. When an order needs a phone number that we do not have, one non-model interactive message asks for it, capped, with the slot released if the send fails.

The ask is deliberately not generated by the agent, so it cannot be phrased away or half-sent. And it is verified against the live platform rather than the docs: the share-contact button renders on a real handset, a real tap completes the flow, and the response carries an origin field that distinguishes a genuine self-share from an arbitrary contact card.

What happened

WhatsApp started letting people use a username instead of exposing their phone number. For a sender who adopts one, the inbound webhook simply does not contain a phone number. The identity lives in different fields.

Our parser read the phone field, found nothing, and skipped the message. One line, no logging:

pythonif not from_number:
    continue

Nothing raised. Nothing was recorded. The error rate did not move, the queues stayed clean, the dead-letter queues stayed empty, and the dashboards stayed green. Around twenty customers a day, across seven tenants, were messaging restaurants and being met with silence.

Why our own runbook made it worse

We had a documented procedure for “this number has gone quiet.” Its second step is to count the inbound messages ever seen for that tenant, and if the count has not moved, conclude that Meta is not calling us and go and look at the platform configuration.

That step is right for every cause we had previously encountered — a webhook subscription that was never made, an app left in development mode, an expired token. It is precisely wrong here, because Meta was calling us, on time, with a valid payload. The count did not move because we deleted the evidence ourselves, four lines before we would have recorded it.

A diagnostic step that distinguishes “they did not call” from “they called and we discarded it” has to read the earliest artifact you persist — the one written before any of your own logic can throw it away. Anything further downstream cannot tell the two apart.

The runbook now begins by querying the deduplication table for that sender. A row with an empty sender field is an immediate, unambiguous answer: this is ours.

The thing that made the fix non-obvious

The instinctive repair is to look the new identifier up and get the phone number back, leaving everything downstream unchanged. That API does not exist. I probed the endpoints directly rather than relying on the documentation, which is a habit I would now defend strongly for anything platform-side.

What I found changed the data model rather than the parser:

  • The identifier is scoped to the business. The same human has a different one at each brand on the platform. A global unique constraint on it — which is what I would have written without checking — would have been quietly, structurally wrong.
  • Identifiers regenerate when the customer changes their phone number, so records silently fork unless you subscribe to the update event.
  • The phone number is only ever available if the customer interacted recently or is already stored, and that store cannot be enumerated and is not retroactive.

So the identifier is not a lookup key for a phone number. It is an address in its own right, and the system had to learn to carry two kinds of address.

Quantifying the blast radius before blocking

Order placement now refuses to proceed for a customer with no phone number. That is a hard block, and hard blocks are the category of guard that has caused the most damage in this system — the order validator is an entry about exactly that.

So before adding it, I counted how many existing customers it could possibly fire on. Zero of 46,166. The gate is safe because it is provably unreachable for anyone already in the database, and that is a sentence I can defend rather than a hope.

Before adding a hard block, measure its false-positive surface against production data. If you cannot state how many existing records it would reject, you are not ready to make it a block.

What is still open

The verification flow uses a template type that rejects these identifiers, so username adopters cannot receive a one-time password. The identity work is built; that consequence is not solved.

The principle

A guard that discards input must log what it discarded. Silence is indistinguishable from the case never occurring, and platform contracts change without asking you.

Lessons

  • I was wrong three times before I asked the right questionMessages were disappearing. Three careful hypotheses, all disproven, before a single query settled it. The generalisable move is asking what the earliest thing you write down is, before your own logic can discard anything.
