## What happened

WhatsApp started letting people use a username instead of exposing their phone number.
For a sender who adopts one, the inbound webhook simply does not contain a phone
number. The identity lives in different fields.

Our parser read the phone field, found nothing, and skipped the message. One line, no
logging:

```python
if not from_number:
    continue
```

Nothing raised. Nothing was recorded. The error rate did not move, the queues stayed
clean, the dead-letter queues stayed empty, and the dashboards stayed green. Around
twenty customers a day, across seven tenants, were messaging restaurants and being
met with silence.

## Why our own runbook made it worse

We had a documented procedure for "this number has gone quiet." Its second step is to
count the inbound messages ever seen for that tenant, and if the count has not moved,
conclude that Meta is not calling us and go and look at the platform configuration.

That step is right for every cause we had previously encountered — a webhook
subscription that was never made, an app left in development mode, an expired token.
It is precisely wrong here, because Meta *was* calling us, on time, with a valid
payload. The count did not move because we deleted the evidence ourselves, four lines
before we would have recorded it.

::: principle
A diagnostic step that distinguishes "they did not call" from "they called and we
discarded it" has to read the earliest artifact you persist — the one written before
any of your own logic can throw it away. Anything further downstream cannot tell the
two apart.
:::

The runbook now begins by querying the deduplication table for that sender. A row with
an empty sender field is an immediate, unambiguous answer: this is ours.

## The thing that made the fix non-obvious

The instinctive repair is to look the new identifier up and get the phone number back,
leaving everything downstream unchanged. That API does not exist. I probed the
endpoints directly rather than relying on the documentation, which is a habit I would
now defend strongly for anything platform-side.

What I found changed the data model rather than the parser:

- The identifier is **scoped to the business**. The same human has a different one at
  each brand on the platform. A global unique constraint on it — which is what I would
  have written without checking — would have been quietly, structurally wrong.
- Identifiers **regenerate when the customer changes their phone number**, so records
  silently fork unless you subscribe to the update event.
- The phone number is only ever available if the customer interacted recently or is
  already stored, and that store cannot be enumerated and is not retroactive.

So the identifier is not a lookup key for a phone number. It is an address in its own
right, and the system had to learn to carry two kinds of address.

## Quantifying the blast radius before blocking

Order placement now refuses to proceed for a customer with no phone number. That is a
hard block, and hard blocks are the category of guard that has caused the most damage
in this system — the
[order validator](/ahmedamer/lessons/validator-blocked-more-orders-than-the-bug/) is an
entry about exactly that.

So before adding it, I counted how many existing customers it could possibly fire on.
Zero of 46,166. The gate is safe because it is provably unreachable for anyone already
in the database, and that is a sentence I can defend rather than a hope.

::: principle
Before adding a hard block, measure its false-positive surface against production data.
If you cannot state how many existing records it would reject, you are not ready to
make it a block.
:::

## What is still open

The verification flow uses a template type that rejects these identifiers, so
username adopters cannot receive a one-time password. The identity work is built; that
consequence is not solved.
